# HoneyBot-IoT — ML Model Card (Module 8)

> **Status (v0.8.2):** Module 8 is implemented. `ml/features.py` builds the labelled
> per-session dataset; `ml/train.py` trains an XGBoost six-class classifier and an Isolation
> Forest with 5-fold cross-validation; `ml/model.py` serves classification, anomaly and a
> 0–100 risk score; `ml/narrator.py` produces the threat narrative; and `ml/ml_api.py` is the
> FastAPI inference microservice (the `ml_api` container). The intel engine scores every
> finished session (`ml/score.py` → `ml_predictions` table) and the dashboard API exposes it
> at `/api/ml/model`, `/api/ml/predictions`, `/api/ml/predictions/{id}` and `/api/ml/risk`.

## Intended use

Automatically label each captured attacker **session** by type, flag novel/zero-day behaviour,
and produce a plain-English threat narrative — removing manual log review for SOC analysts.

## Data

- **Source:** the `events` table of this honeypot (one row per interaction), aggregated to one
  feature vector per `session_id`.
- **Labels (weak):** the rule engine (`intel/rules.py`) already assigns an attack type to each
  session; these become the weak labels. The scope's "200,000+ labelled Cowrie sessions" is
  **not** a ready-made labelled set — we will state honestly that labels come from
  **rule-based weak labelling + self-generated simulated attacks + live-collected traffic.**
- **Simulated labelled traffic:** `tests/simulate_attacks.py` produces traffic for every class.

## Features (per session)

duration · auth attempts · distinct usernames/passwords · successful-login ratio · command
count · presence of `wget`/`curl`/`chmod`/`busybox`/`/tmp` · number of captured URLs · distinct
protocols · ports touched · inter-arrival-time stats · MQTT publishes to control topics · HTTP
404 count.

## Classes (6)

`brute-force · malware delivery · botnet C2 · port scan · protocol exploit · normal`
(the mapping from rule detections to these classes is in `docs/MILESTONE_60.md §5`.)

## Models (implemented)

| Component | Algorithm | Output | Where |
|---|---|---|---|
| Attack classifier | XGBoost (160 trees, depth 5) | class + confidence + full class probabilities | `ml/train.py`, `ml/model.py` |
| Anomaly detector | Isolation Forest (200 trees) | 0–1 novelty score (1 = most anomalous) | `ml/train.py`, `ml/model.py` |
| Risk score | transparent blend of class severity × confidence and anomaly | 0–100 per session, aggregated per device | `ml/model.py` `risk_score()` |
| Threat narrator | template (offline, default) or GPT-4o / local Ollama LLaMA | 3-paragraph narrative + recommendations | `ml/narrator.py` |

## Evaluation (5-fold stratified cross-validation)

Trained on a **synthetic baseline** of 3 000 sessions (500/class generated by `ml/synth.py`,
schema-identical to live data) so the pipeline runs and is demonstrable from day one; live
honeypot sessions augment or replace it as they accrue (`python -m ml.train`).

| Metric | Target | Synthetic baseline |
|---|---|---|
| Accuracy (mean ± std) | > 85% | **0.995 ± 0.002** |
| Per-class F1 | — | 0.99–1.00 all six classes |
| Inference latency | < 100 ms/session | ~1–3 ms (XGBoost `predict_proba`) |

**Honesty note (important for the viva).** The ~0.99 figure is high *because the synthetic
classes are well-separated by their dominant engineered features* (e.g. brute-force has many
distinct passwords, malware-delivery has `wget`+`chmod`+busybox, botnet-C2 has heavy MQTT or
ICS state changes). It validates the feature engineering and the training/serving pipeline, it
is **not** a claim about real-world accuracy. The meaningful evaluation is on **live, adversarial
traffic**, where overlapping and evasive sessions will push accuracy down toward the ≥85% target;
that measurement is ongoing data collection. The weak labels come from the rule engine, so the
model can partly *learn the rules* — the top features (`cmd_download`, `download_attempts`,
`mqtt_publishes`, `http_404`, `auth_attempts`, `mean_cmd_len`) include timing/ratio signals the
rules do **not** use, which is what lets it generalise beyond them.

## Limitations

- Accuracy on live data depends on volume and will be lower than the synthetic baseline until
  enough real sessions are collected (scope **LI-6**); report the real number when available.
- The LLM narrator needs internet for GPT-4o unless local Ollama is configured; the default
  **template** backend is fully offline (**LI-7**) and is what the honeynet uses.
- **Predictive scoring (M8-FE-4):** delivered as the transparent 0–100 risk score and 24-h
  per-device aggregation rather than a trained LSTM. A deep time-series forecaster is deferred
  as future work — it needs far more longitudinal live data than a lab run provides, and a
  transparent, explainable score is more defensible for a SOC than an unvalidated black box.
